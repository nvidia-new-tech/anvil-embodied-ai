# 執行推論

所有的推論情境都是透過 `scripts/run_inference.sh` 執行的。

> **要部署一個不是自己訓練的 checkpoint？** 先讀
> [Checkpoint 驗收流程](checkpoint驗收流程.md)。這份文件涵蓋怎麼跑起整套服務；
> 那份文件涵蓋怎麼判斷一個 checkpoint 該用哪個 config，以及兩者對不上時會出現
> 的靜默失敗模式。先從 `scripts/preflight_checkpoint.py` 開始。

> **想看這週新增了什麼？** [本週進度.md](本週進度.md) 整理了新的 benchmark
> 計分工具、model zoo 整理、benchmark 結果、這次順便修好/發現的 inference
> 問題，以及下面 `--dev-src` 這則備註的完整脈絡。

**先把 `.env.example` 複製成 `.env`，再依你的環境編輯：**

```bash
cp .env.example .env
# 然後編輯 .env
```

### `.env` 變數

`.env` 是主要的設定檔——設一次就能重複使用。關鍵變數：

| 變數 | 是否必要 | 說明 |
|----------|----------|-------------|
| `MODEL_PATH` | 是（推論） | Checkpoint 資料夾在 host 上的路徑。必須是絕對路徑或以 `./` 開頭——單純的相對路徑會被當成 Docker 的 named volume。 |
| `ROS_DOMAIN_ID` | 是 | ROS2 domain ID——必須跟 Anvil Devbox 一致。只在 localhost 上跑就留空。 |
| `CYCLONEDDS_URI` | 是 | CycloneDDS XML config 的路徑（例如 `configs/cyclonedds/two_pc_gpu.xml`）。 |
| `LEROBOT_EXTRAS` | 僅 VLA 需要 | 逗號分隔、烤進 Docker image 裡的 policy extras——例如 `smolvla`、`pi,smolvla`。**改了之後要重建 image：** `docker compose build`。ACT 和 Diffusion 留空即可。 |
| `HF_CACHE` | 僅 VLA 需要 | HuggingFace model cache 在 host 上的路徑（預設：`~/.cache/huggingface`）。Pi0、Pi0.5、SmolVLA 都需要——它們執行期會載入 PaliGemma tokenizer。 |
| `CONFIG_FILE` | 是 | 推論 config YAML 的路徑（預設：`configs/lerobot_control/inference_default.yaml`）。 |
| `ACTION_TYPE` | 否 | 只會傳給**推論監控節點**（`inference_monitor_node`）。主推論節點永遠是透過 `resolve_action_type()` 從 checkpoint 裡的 `anvil_config.json` 讀取——這個環境變數**不會**覆蓋它。選項：`absolute`、`delta_obs_t`、`delta_sequential`。 |
| `ECHO_TOPIC_ONLY` | 否 | `true` = 跳過模型載入，只訂閱 topic 並記錄 FPS。用來在沒有 GPU 或 checkpoint 的情況下驗證 DDS 連線。等同於 `--echo-topic-only`。 |
| `MONITOR_ENABLE` | 否 | `true` = 啟用推論監控節點（記錄逐步 CSV + PNG 報告）。等同於 `--monitor-enable`，但不含該旗標附帶的結束時自動繪圖與輸出目錄預先建立。 |
| `DEBUG` | 否 | `true` = 啟用額外指標：動作平滑度、佇列深度統計、Action FPS。 |

完整說明與預設值見 [`.env.example`](../.env.example)。

### 腳本旗標

這些旗標是不用編輯 `.env` 就能在命令列上覆蓋行為的輕量方式：

```bash
./scripts/run_inference.sh [--fake-hardware] [--monitor-enable] [--echo-topic-only] [--debug] [--dev-src] [--no-benchmark] [COMPOSE_ARGS...]
```

| 旗標 | 作用 |
|------|-------------|
| `--fake-hardware` | 切換成 `docker-compose.fake-hardware.yml`——在本機透過 bridge network 模擬雙 PC 架構（CycloneDDS，沒有真實機器人）。 |
| `--monitor-enable` | 在 compose 指令加上 `--profile monitor`。在正式環境（非 fake-hardware）模式下還會匯出 `MONITOR_ENABLE=true`、以目前使用者身份預先建立輸出目錄，並在結束時自動繪圖。 |
| `--echo-topic-only` | 匯出 `ECHO_TOPIC_ONLY=true`——只訂閱 topic 並記錄 FPS，不載入模型或用 GPU。等同於在 `.env` 設定 `ECHO_TOPIC_ONLY=true`。 |
| `--debug` | 匯出 `DEBUG=true`——啟用額外指標：動作平滑度、佇列深度統計、Action FPS。等同於在 `.env` 設定 `DEBUG=true`。 |
| `--dev-src` | 把 `ros2/src/lerobot_control` 掛載蓋過 image 內建的版本（見 `docker-compose.devsrc.yml`），讓工作目錄裡的改動不用重建就能跑。**測試備註：** 解除安全協定的限制（依照官方建議的方式）之後，用 `--dev-src` 跑起來的動作明顯比較確實——先前疑似是安全限制把動作幅度/速度壓得太保守，導致執行看起來猶豫、不夠確實。**這個旗標只是為了避免重建 image 的權宜之計**——等這批改動（含上面這次安全協定調整）重新 `docker compose build` 烤進 image 之後，就不再需要加 `--dev-src`，直接跑 image 內建的版本即可。 |
| `--no-benchmark` | 不要自動啟動原本會跟著 `up` 一起開的 benchmark 計分網頁（見 [tools/README.md](../tools/README.md)）。`BENCHMARK_PORT`（預設 `8777`）可以改它的 port。 |

## Preflight：讓 Checkpoint 跟 Config 對上

在手臂上電之前先做這件事，尤其是部署一個不是自己訓練的 checkpoint 時。

**Checkpoint 跟它的推論 config 之間，每一種對不上的方式都會靜默失敗。** 不會
raise、不會警告，手臂還是會做出看起來合理的動作。2026-08-20 到 09-04 那次除錯，
問題全部都屬於這一類——沒有一個是模型品質的問題。

```bash
uv run scripts/preflight_checkpoint.py <checkpoint_dir> --config <inference_yaml>

# 範例
uv run scripts/preflight_checkpoint.py \
    /srv/shared/model_zoo/anvil/macp_20260813__pass/pi05_bottle_handoff/checkpoints/last \
    --config configs/lerobot_control/inference_flip.yaml

# 只掃描權重，還沒有 config 可以比對的情況
uv run scripts/preflight_checkpoint.py <checkpoint_dir> --skip-weight-scan
```

它會讀取 checkpoint 自己的 `config.json` + `anvil_config.json`，跟 YAML
交叉比對。**Exit code 1 = 不要啟動。**

| 檢查項目 | 錯了會實際發生什麼事 |
|-------|-------------------------------------|
| 相機集合是否符合 `observation.images.*` | Checkpoint 宣告但 config 沒列的相機，會被補上一張**全 -1 的空白影像、mask 為 0**（`modeling_pi05.py:1199-1202`）。不會報錯。Policy 看到的是一張灰色畫面，動作會慢慢退化成一個接近固定的姿勢。 |
| Config 裡沒有*多餘*的相機 | `has_complete_observation()` 永遠回傳 False，inference 永遠不會開始。`multi_process.py:306` 會組出一個 `"waiting for cameras: [...]"` 字串——但整個 repo 裡**從來沒有任何地方呼叫** `get_incomplete_reason()`，所以這個診斷資訊算出來就被丟掉了。整個 run 就這樣卡著。 |
| `observation.state` 的寬度 | pi0/pi05 會把 state 補到 `max_state_dim`（**32**，`configuration_pi05.py:41`），再把 action 截斷回去。一個 8-DOF 的 checkpoint 被餵進 16 DOF 的資料，會把左手臂的值讀進右手臂的位置，而且**動作看起來依然合理**。 |
| `arms.*.action_start/end` 是否在真實的 action 寬度內 | 多出來的部分會靜默地發布**全零**。 |
| 切片寬度是否等於 `model_joint_order` 的長度 | 關節會在切片裡錯位 N 格。 |
| `task_description` 是否符合 `anvil_config.json` | 語言 token 是一個**conditioning input**——pi0.5 會把它拼進 prompt 裡。改寫過的字串會讓動作變差，而且不會有任何回報。 |
| 權重裡有沒有 NaN/Inf | 有 NaN 的 checkpoint 一樣會產生動作，只是是錯的。 |
| `queue_trigger_threshold` ≤ `chunk_size` | 佇列永遠存不到那麼多，導致每一步都重新觸發推論。 |
| `safety.max_relative_target` 的形狀 | 見[安全限制](#safety-limits)——純量會讓夾爪一步就關閉，手臂卻還被節流。 |

### 不用機器人也能定位輸入端的問題

如果 policy 有跑但表現不對，這個方法可以在花更多機器人時間之前，先分辨是輸入
pipeline 壞掉還是權重本身的問題。

離線跑一次 `predict_action_chunk`，用**跟 ROS 節點完全一樣的方式**組出 batch，
再算輸出的時間比率。如果離線 pipeline 算出來的結果接近 ground-truth 比率
（在 `pi05-flip` 上量到約 0.14，對照 GT 是 0.152），但實際跑在 ROS 上的
pipeline 明顯偏低，問題就在**輸入端**——相機的 key、state 組裝、正規化——
不是 checkpoint 本身。

同一招也可以拿來量化相機的依賴程度：把某支相機換成全 -1 的空白影像、重新算
比率，就能得到失去那個視角的成本。這很有用，因為缺相機這件事本身是靜默的
（見上面的表格）。

### 從 Checkpoint 推導出 Config

| 推論 YAML | 真正的資料來源 |
|----------------|-----------------|
| `cameras.mapping` 的值 | `config.json` → `input_features` 裡的 `observation.images.*`，**一字不差** |
| `joint_names.arm_mapping` | `observation.state` 的形狀 ÷ 每隻手臂的關節數——單手臂 ⇒ 只有**一個** key |
| `joint_names.model_joint_order` | 資料轉換 config；必須符合訓練時的順序 |
| `arms.*.action_start/end` | `output_features.action` 的形狀 + 手臂配置 |
| `model.task_description` | `anvil_config.json`——留 `null` 讓它自動讀取（建議） |

> **單手臂 vs 雙手臂。** 雙手臂的 checkpoint 會餵進 16-DOF 的 state，並發布
> `action[8:16]`。單手臂的 checkpoint 宣告的是 `observation.state [8]` /
> `action [8]`，所以 `arm_mapping` 只列一隻手臂，切片是 `action[0:8]`。複製
> 雙手臂的 config、只換 `MODEL_PATH`，會同時在**兩個方向**上都靜默地是錯的。
> 對照範例見
> [`shapes/1arm_2cam.yaml`](../configs/lerobot_control/shapes/1arm_2cam.yaml)
> 和
> [`shapes/2arm_3cam.yaml`](../configs/lerobot_control/shapes/2arm_3cam.yaml)。

> **絕對不要在推論端重新計算正規化統計量。** 這些統計量已經烤進 checkpoint
> 裡了，所以 `make_pre_post_processors(pretrained_path=<ckpt>)` 才是對的做法。
> 從資料集重新計算會拿到*沒有被 floor 過*的統計量，靜止手臂的輸出會爆掉——見
> [State pinning](#state-pinning-degenerate-state-dims)。

### `model_card.yaml` 必須包含什麼

訓練端的欄位（`steps`、`batch_size`、`created_by`）跟上面這些都無關。要讓一個
沒參與訓練過程的人也能部署這個 checkpoint，卡片需要包含：

```yaml
cameras: [chest, wrist_l, wrist_r]   # 一字不差的 observation.images.* key
state_dim: 16
action_dim: 16
arms:
  left:  {action_start: 0,  action_end: 8,  driven: false}   # 靜止手臂：保持不動，不要追蹤
  right: {action_start: 8,  action_end: 16, driven: true}
action_type: absolute                 # absolute | delta_obs_t | delta_sequential
task_description: "Flip the package upside down."   # 一字不差，是 conditioning input
chunk_size: 50
n_action_steps: 50
stats_floor: 0.03                     # 如果資料集的統計量有被 floor 過
inference_config: configs/lerobot_control/inference_flip.yaml   # 上一次確認能跑的 config
```

`cameras` 是風險最高的欄位——多送一支相機模型會直接忽略，少送或拼錯字才是致命
的方向。`arms[].driven` 很重要，因為一個訓練時某隻手臂完全不動的雙手臂
checkpoint，對那隻手臂輸出的其實是「保持這個姿勢」，**不是**一個要去追蹤的
目標；去追蹤它會把靜止的手臂帶往一個統計上的平均姿勢。`inference_config`
是讓一個 checkpoint 能重新被部署、成本最低的單一欄位。

### State pinning（狀態退化維度的處理）

只要有一隻手臂在整個任務期間都是靜止的，就需要這個機制。把那隻手臂的 state
維度凍結在訓練時的中位數，而不是餵進即時的編碼器讀值：

```yaml
state_pinning:
  enabled: true
  arms: [l]        # 要釘住的 arm_mapping key
  source: q50      # q50 | mean，從 checkpoint 自己的 normalizer 統計量讀取
  # values: [...]  # 可選的明確覆寫值，每個被釘住的維度各一個
```

**為什麼需要這樣做。** 一個在訓練時從來不動的關節，`q99 − q01` 會退化成一個
很小的值，資料集統計量的下限會把它加寬到 `0.03`。QUANTILES 正規化的公式是
`2·(x − q01)/(q99 − q01) − 1`（`normalize_processor.py`，QUANTILES 分支），
所以這些維度的運算增益大約是 `2/0.03 ≈ 67` 單位/rad，相對於真的會動的手臂
是 1.3–2.6——敏感度高了約 35 倍。訓練時的休息姿勢跟部署時只要差不到一度，
這個維度就會超出正規化後的 `[-1, 1]` 範圍，而且 **`normalize_processor.py`
裡完全沒有 clamp 或 clip**（已確認：整個檔案裡沒有任何 `clamp`/`clip` 呼叫）。

**為什麼這對 pi0.5 是致命的，但 SmolVLA 沒事。** pi0.5 會把正規化後的
state 離散化成 256 個 bin，拼進**文字 prompt**（`processor_pi05.py:75-81`）：

```python
discretized_states = np.digitize(state_np, bins=np.linspace(-1, 1, 256 + 1)[:-1]) - 1
full_prompt = f"Task: {cleaned_text}, State: {state_str};\nAction: "
```

低於 `-1` 會得到 token **`-1`**——prompt 字串裡出現字面上的 `"-1"`，這是訓練
時從來沒出現過的東西。高於 `+1` 則會飽和到 **`255`**。兩種情況都會污染那個
用來 conditioning 整個 action chunk 的 prefix——**是兩隻手臂都受影響，不只是
被釘住的維度**。步驟順序是刻意設計、而且缺一不可的：`processor_pi05.py:141`
有一條註解寫著*「NormalizerProcessorStep 必須排在
Pi05PrepareStateTokenizerProcessorStep 之前」*。

SmolVLA 剛好相反：它的 `TokenizerProcessorStep` 是在
`NormalizerProcessorStep` **之前**執行的（`processor_smolvla.py:69-85`），
state 是透過 `nn.Linear`（`modeling_smolvla.py:693`）進到模型裡的。超出範圍
只是一個偏大的浮點數，會平滑地劣化，不會變成一個錯誤的 token。這就是為什麼
同一份資料下，`smolvla-flip` 沒事而 `pi05-flip` 出了問題。

**觀察到的現象：** 右手夾爪卡在 0.048–0.053，而不是伸到 −0.003。部署時的姿勢
左邊 j2 = −0.194 rad，正規化後是 −1.84，會被 token 化成 `-1`。

把值釘在 `q50`，能讓每個被釘住的維度正好落在正規化後的 `0.0`（token 128），
所以 prompt 裡 state 的部分每一步都會是位元組完全相同的。這些值是從
checkpoint 的 `policy_preprocessor.json` → `normalizer_processor` 的
safetensors 讀出來的，所以不會跟權重本身脫節。設 `enabled: false` 可以改回
餵即時的 state，拿去跟 SmolVLA 做 A/B 對照。

這也順便關掉了一條靜默路徑：`_build_observation` 原本對任何
`/joint_states` 裡缺的關節都預設成 `0.0`。以左邊 j4（`q01 = 1.574`）
來說，這會正規化成 **−105.9**，而且完全不會有警告。

<a id="safety-limits"></a>
**安全限制：**

這兩層都是照著上游 LeRobot 的 `openarm_follower.send_action`
（`openarm_follower.py:276-290`）做的，而且都是可選的——省略一整個區塊就等於
關掉它。

```yaml
safety:
  # 每一步的位移上限。純量會讓每個關節套用相同的上限；正確的寫法應該是
  # 逐關節的對應（見下方的警告）。
  max_relative_target:
    joint1: 0.1
    # ... joint2..joint7 依此類推
    finger_joint1: 0.005
  # 逐關節的絕對邊界。這裡不假設任何預設值——上游是照著它自己的 bus 和單位
  # 給值的，直接套用在這裡會是錯的。要從 URDF 裡填。
  # joint_limits:
  #   joint1: [-3.14, 3.14]
  #   finger_joint1: [0.0, 0.05]
```

> ⚠ **這個 action 向量混合了不同的單位。** `joint1..joint7` 是弧度；
> `finger_joint1` 是**線性移動、單位是公尺**，行程大約 0.05 m。一個純量
> 沒辦法同時服務這兩者。純量 `0.1` 會把手臂節流到 7–18 步的行程，但同時
> *超過夾爪的整個行程範圍*，所以夾爪會在手臂還在下降的時候一步就完全合起來
> ——手臂根本還沒碰到物體，夾爪就先關了。在 `monitor_output` 上量到的數據：
> 在 approach 階段，手臂有 85% 的步數都被節流限制住，夾爪關閉時距離指令姿勢
> 還有 0.060 rad。`finger_joint1: 0.005` 能給大約 10 步（0.33 秒）的時間
> 合起來，讓夾爪跟手臂的速度同步。

> **被移除的欄位。** `max_position_delta` 已經被 `max_relative_target`
> 取代。`min_position_delta`（一個上游沒有對應機制的 deadband）已經整個
> 移除——一個看起來合理的值會讓夾爪永久凍結。節點現在遇到這兩個欄位任一個
> 都會直接報錯，而不是靜默地忽略這個限制。

**影像解析度：** 畫面是以 640×480 儲存的，模型內部會 resize 成 224×224。
送原生解析度就好——不要事先縮放。

## DDS Middleware 選擇

Fast DDS 和 CycloneDDS 都支援。**CycloneDDS 是預設值**（在我們的測試中比較快）。

> ⚠ **兩邊必須用同一種 RMW**——混用 Fast DDS 和 CycloneDDS 等於完全找不到
> 對方（不會報錯，就是安靜地沒有反應）。

| 部署方式 | `RMW_IMPLEMENTATION` | `CYCLONEDDS_URI` | anvil-loader `.env.config` |
|-----------|----------------------|------------------|---------------------------|
| **單 PC · CycloneDDS**（*預設*） | `rmw_cyclonedds_cpp` | `file://.../single_pc.xml` | `ENABLE_CYCLONEDDS=true`<br>`CYCLONEDDS_PEER_IP=127.0.0.1` |
| 單 PC · Fast DDS | `rmw_fastrtps_cpp` | *（忽略）* | `ENABLE_CYCLONEDDS=false` |
| 雙 PC · CycloneDDS | `rmw_cyclonedds_cpp` | `file://.../two_pc_gpu.xml` | `ENABLE_CYCLONEDDS=true`<br>`CYCLONEDDS_PEER_IP=<gpu_pc_ip>` |

所有 CycloneDDS 的 config 都放在 `configs/cyclonedds/`。`docker-compose.yml`
和 `.env.example` 裡的預設值是針對單 PC CycloneDDS——要切換模式就在 `.env`
裡覆蓋。

## 部署拓樸

### 單 PC —— 推論和 workcell 在同一台機器上

```
  同一台機器
┌────────────────────────────────────────────────────────────┐
│  anvil-loader (ros2_control)       anvil-embodied-ai       │
│  joint_states (500 Hz)  ◄─────────  inference_node (30 Hz) │
│  cameras (4× 30 Hz)      CycloneDDS  action commands       │
│                           (host net)                       │
└────────────────────────────────────────────────────────────┘
```

兩邊都在 host network 上用 CycloneDDS——multicast 會自動處理彼此的探索。在
anvil-loader 的 `.env.config` 裡設定：
```
ENABLE_CYCLONEDDS=true
CYCLONEDDS_PEER_IP=127.0.0.1
```

### 雙 PC —— GPU PC 跟機器人 PC 分開

```
  Anvil Devbox (anvil-loader)             CycloneDDS              GPU PC (anvil-embodied-ai)
┌─────────────────────────────┐    ┌────────────────────┐    ┌─────────────────────────────┐
│  ros2_control               │    │                    │    │  lerobot_control            │
│  joint_states (500 Hz)      │◄───┤  Gigabit Switch    ├───►│  inference_node (30 Hz)     │
│  cameras (4× 30 Hz)         │    │                    │    │  action commands            │
└─────────────────────────────┘    └────────────────────┘    └─────────────────────────────┘
```

設定 `CYCLONEDDS_URI=file:///workspace/configs/cyclonedds/two_pc_gpu.xml`，
並在 `two_pc_gpu.xml` 和 anvil-loader 的 `.env.config` 裡都設好 peer IP。
網路設定的完整說明見[完整文件](https://docs.anvil.bot/)。
