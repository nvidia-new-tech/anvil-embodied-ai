# 末端空間推論（EE-space）

怎麼分辨、怎麼設定、怎麼驗證末端空間與關節空間這兩條推論路徑。

一般的推論流程見 [執行推論.md](執行推論.md)，checkpoint 驗收見
[checkpoint驗收流程.md](checkpoint驗收流程.md)。這份只講兩者的差別。

---

## 兩條路徑的差別

| | 關節空間（預設） | 末端空間（EE） |
|---|---|---|
| 模型輸出 | 8 個關節位置 | `[x, y, z, qx, qy, qz, qw, gripper]` |
| 夾爪在第幾維 | **dim 0**（`finger_joint1` 在最前） | **dim 7**（最後） |
| 發布訊息 | `std_msgs/Float64MultiArray` | `anvil_msgs/CommandedEEPose` |
| 發布 topic | `/follower_r_forward_position_controller/commands` | `/commanded_ee_right` |
| shape config | `shapes/1arm_2cam.yaml` | `shapes/1arm_2cam_ee.yaml` |
| 限幅程式 | `action_limiter.py` | `ee_pose_limiter.py` |
| loader 設定 | `openarm_v2_inference.yaml` | `openarm_v2_inference_commanded_ee.yaml` |

`observation.state` **兩者都是關節空間的 8 維**。只有 action 改變。

---

## 先確認你的 checkpoint 是哪一種

### ⚠️ preflight 分辨不出來

`preflight_checkpoint.py` 比對的是**寬度**（8 == 8），而 `config.json` 的
`output_features.action` **沒有 `names` 欄位**。兩種 checkpoint 對上任一
config 都會回報 `All checks passed`。這點實測確認過：關節空間的
`smolvla_pack_pick_place_20260917` 對上 `1arm_2cam_ee.yaml` 一樣全過。

用錯的後果是關節角度（弧度）被當成公尺與四元數發出去。

### 可靠的判別方式：看 normalizer 的夾爪維度

夾爪的行程是 `[-0.003, 0.05]` 公尺，這個範圍在兩種 checkpoint 裡都認得出來，
差別在它**落在第幾維**：

```bash
./.venv/bin/python -c "
from safetensors.numpy import load_file
import numpy as np, glob, sys
d = sys.argv[1]
f = glob.glob(d + '/policy_postprocessor_step_*_unnormalizer_processor.safetensors')[0]
x = load_file(f)
mn = np.asarray(x['action.min']).ravel()
mx = np.asarray(x['action.max']).ravel()
print('action.min:', np.array2string(mn, precision=3, suppress_small=True))
print('action.max:', np.array2string(mx, precision=3, suppress_small=True))
print()
print('dim 0 範圍:', f'{mn[0]:+.4f} .. {mx[0]:+.4f}')
print('dim 7 範圍:', f'{mn[7]:+.4f} .. {mx[7]:+.4f}')
print('→ 夾爪 [-0.003, 0.05] 落在 dim 0 = 關節空間；落在 dim 7 = 末端空間')
" model_zoo/<你的checkpoint>
```

實際數字，供對照：

```
關節空間 (smolvla_pack_pick_place_20260917/005000)
  dim 0: -0.0030 .. +0.0500   ← 夾爪
  dim 7: -1.2149 .. +1.4004   ← joint7，弧度

末端空間 (smolvla_pack_pick_place_eef_5000)
  dim 0: +0.1509 .. +0.5002   ← x，公尺
  dim 7: -0.0011 .. +0.0517   ← 夾爪
```

`anvil_config.json` 的 `note` 通常也會寫（例如 `"EE-space action"`），但那是人寫的
字串，會過期也會漏；normalizer 是從訓練資料算出來的，不會騙人。

## 末端空間推論需要的四樣東西

缺任何一樣都**不會報錯**，只會安靜地不動或走錯路徑。

### 1. EE 空間訓練的 checkpoint

見上一節。用關節空間的 checkpoint 配 EE config，preflight 照樣會過。

### 2. `.env` 指向 EE 的 config

```bash
MODEL_PATH=/path/to/model_zoo/smolvla_pack_pick_place_eef_5000
CONFIG_FILE=./configs/lerobot_control/shapes/1arm_2cam_ee.yaml
IMAGE_TAG=ee-space
```

### 3. 映像裡要有 `anvil_msgs`

`inference_node.py` 的 import 是有保護的：

```python
try:
    from anvil_msgs.msg import CommandedEEPose
except ImportError:
    CommandedEEPose = None
```

所以**訊息套件缺失時程式不會崩潰**。`CommandedEEPose` 變成 `None`，
`msg_type == "CommandedEEPose"` 的比對永遠不成立，EE 手臂被從發布路徑
悄悄拿掉，日誌沒有任何線索。

驗證：

```bash
docker run --rm --entrypoint /entrypoint.sh \
  ghcr.io/anvil-robotics/lerobot-inference:ee-space \
  python3 -c "from anvil_msgs.msg import CommandedEEPose; print('ok')"
```

**怎麼做出這個映像** —— 完整 rebuild 會重跑約 9 GB 的 pip 安裝，網路慢的話要好幾
小時，而且如果 `LEROBOT_EXTRAS` 沒設（`docker-compose.yml` 預設空字串），
SmolVLA 會安靜地不被安裝。所以可以只編譯訊息套件再 commit：

```bash
docker run -d --name ee-build \
  -v "$PWD/ros2/src/anvil_msgs":/workspace/src/anvil_msgs:ro \
  --entrypoint sleep ghcr.io/anvil-robotics/lerobot-inference:latest 900

docker exec ee-build bash -c '
  source /opt/ros/jazzy/setup.bash
  cd /workspace && colcon build --packages-select anvil_msgs \
    --cmake-args -DCMAKE_BUILD_TYPE=Release'

docker commit \
  --change 'ENTRYPOINT ["/entrypoint.sh"]' \
  --change 'CMD ["ros2", "launch", "lerobot_control", "inference.launch.py"]' \
  --change 'WORKDIR /workspace' \
  ee-build ghcr.io/anvil-robotics/lerobot-inference:ee-space

docker rm -f ee-build
```

約五秒、不需要網路。三個 `--change` 不能省 —— `docker commit` 會把建置容器的
`--entrypoint sleep` 一起存進映像。

也**不要**刪 `/workspace/build`：那不是暫存目錄，`lerobot_control` 是 develop
模式安裝的，`build/lerobot_control/lerobot_control` 是指向 `src/` 的 symlink，
刪掉會讓 `import lerobot_control` 直接失敗。

⚠️ 這樣做出來的映像**只多了 `anvil_msgs`**，`lerobot_control` 仍是編譯映像時
的舊版。所以還需要第 4 樣，或是正式 rebuild。

### 4. `docker-compose.override.yml` 把新原始碼掛進去

```yaml
services:
  inference:
    volumes:
      - ./ros2/src/lerobot_control:/workspace/src/lerobot_control:ro
```

因為 develop 安裝的關係，掛載 `src` 就會生效。正式 `docker compose build` 之後
這個檔案就可以刪掉。

### 5.（loader 端）`commanded_ee: true`

沒有這個旗標，`/commanded_ee_right` **根本不存在**，推論會把指令發到沒人訂閱
的 topic，手臂完全不動。

```bash
# anvil-loader/.env.config
ARMS_CONTROL_CONFIG_FILE=openarm_v2_inference_commanded_ee.yaml
```

驗證接收端存在：

```bash
docker run --rm --network host -e ROS_DOMAIN_ID=0 \
  -e RMW_IMPLEMENTATION=rmw_cyclonedds_cpp \
  -e CYCLONEDDS_URI=file:///workspace/configs/cyclonedds/single_pc.xml \
  -v "$PWD/configs":/workspace/configs:ro \
  --entrypoint /entrypoint.sh ghcr.io/anvil-robotics/lerobot-inference:ee-space \
  bash -lc 'sleep 6; ros2 topic info /commanded_ee_right'
```

`Subscription count` 要 ≥ 1。同時 `/ee_pose_right`（手臂實際位姿）也會出現，
那個在驗證時很有用。

> **未驗證**：在 `ros2:1.2.7` 裡，唯一引用 `CommandedEEPose` 的是編譯過的
> `quest_teleop` 模組 —— `control/workcell_config.py:93` 只宣告了這個欄位。
> 也就是 EE 指令路徑實際走的是 VR 遙操作節點，而它以 priority 0 取得控制權。
> 接著 Quest 頭盔跑推論時，兩者會競爭同一條路徑，這個互動沒有測過。
> 保險起見，跑 EE 推論時把 Quest 拔掉或設 `ENABLE_VR_TELEOP=false`。

## 安全限制：兩條路徑差很多

### 關節空間：完全沒有限制

```yaml
safety:
  max_relative_target: null    # 沒有每步位移上限，模型輸出原封不動送到控制器
  joint_limits: null           # 沒有關節角度上限
```

`joint_limits` 不能照抄 upstream 的預設值：鍵名不同（upstream 是
`joint_1..joint_7` / `"gripper"`），單位也不同（upstream 的
`"gripper": (-5.0, 0.0)` 是負值閉合，而 `finger_joint1` 是 0~0.05 m 正值開啟，
照抄會把夾爪永久夾死）。要用的話從這台機器的 URDF 填。

### 末端空間：`ee_pose_limiter.py`

**有做的：**
- 四元數正規化（這不是安全功能 —— 非單位四元數根本不是合法旋轉）
- 夾爪夾限到 `[-0.003, 0.05]`
- 每步位移夾限到 `max_position_delta_m`

**明確沒做的：**
- **沒有旋轉速度限制。** 作者的說明是：沒有經過驗證的安全上限，硬編一個
  「未經審查但看起來合理」的值比誠實的空缺更危險，因為它會讓人去信任錯的東西。
- **不與手臂實際位姿比對。** 位移夾限是相對於 **limiter 自己上一次的輸出**，
  不是讀 `/ee_pose_right`。所以：

```python
if self.max_position_delta_m is not None and self._last_position is not None:
```

**第一次呼叫時 `_last_position` 是 `None`，整個夾限被跳過** —— 啟動後的第一個
指令完全不受限制，手臂可能從當下位置直接跳到模型輸出的任何地方。

## 驗證方法：乾跑（dry run）

在讓手臂動之前，用真實相機與關節狀態跑完整推論，但把指令發到一個沒人訂閱的
topic。手臂不會收到任何東西。

```bash
sed 's|command_topic: "/commanded_ee_right"|command_topic: "/commanded_ee_right_DRYRUN"|' \
  configs/lerobot_control/shapes/1arm_2cam_ee.yaml > /tmp/dryrun.yaml

CONFIG_FILE=/tmp/dryrun.yaml CONTROL_FREQ=30.0 docker compose up -d
```

然後訂閱 `/commanded_ee_right_DRYRUN` 觀察。要看的：

1. **第一個指令與 `/ee_pose_right` 的距離** —— 這是上面那個「第一個指令不受限制」
   的實際風險值。實測過一次是 **23.2 mm**，遠小於理論最壞情況（訓練範圍的邊角，
   約 0.3 m）。
2. **後續每步位移** —— 對照 `max_position_delta_m`，看 limiter 是否持續在截斷。
3. **四元數範數** 應為 1.0（證明 limiter 真的在跑，模型原始輸出不會剛好是單位四元數）。
4. **夾爪** 應在 `[-0.003, 0.05]` 內。

⚠️ 乾跑是**開迴路**：手臂不動，`observation.state` 永遠停在同一點，模型每次都從
同一個起點重新規劃，chunk 之間的不連續會被完整計入。閉迴路時手臂會跟上、狀態
會更新，不連續會小很多。**所以乾跑量到的步距是上界，不是目標值。**

用完記得刪掉臨時 config，別讓它留在 repo 裡被誤用。

---

## `max_position_delta_m` 怎麼選

預設 `0.005`（5 mm/tick）被原作者標註為 UNVALIDATED。實測（30 Hz、400 樣本、
開迴路）模型未受限時的每步位移：

| | 位移 | 速度 @30Hz |
|---|---|---|
| p50 | 5.44 mm | 163 mm/s |
| p90 | 12.4 mm | 373 mm/s |
| p99 | 25.9 mm | 776 mm/s |
| max | 40.7 mm | 1221 mm/s |

5 mm 會截斷 **55%** 的步，連中位數都過不了。而且這個夾限會**自我維持**：它夾的
是相對於自己上一次的輸出，一旦開始截斷，`_last_position` 就落後於模型的計畫，
下一步差距更大，於是繼續截斷 —— 軌跡變成由 limiter 決定，不是由策略決定。

選值時記得這是唯一的速度防線（沒有旋轉限制），而且乾跑數字是上界。

## 啟動

```bash
# 1. loader（會自動 homing，手臂會動 —— 先確認周圍淨空）
cd ~/Desktop/anvil/anvil-loader && docker compose up -d

# 2. 確認接收端存在（見上面的 ros2 topic info 指令）

# 3. 乾跑，量第一跳距離

# 4. 正式跑，從低頻率開始，人在急停旁邊
cd ~/Desktop/anvil/anvil-embodied-ai
MODEL_PATH=$PWD/model_zoo/<EE的checkpoint> \
CONFIG_FILE=./configs/lerobot_control/shapes/1arm_2cam_ee.yaml \
CONTROL_FREQ=5.0 ./scripts/run_inference.sh --monitor-enable up
# 穩定後往上：10 → 20 → 30
```

`CONTROL_FREQ` 提高時，**每步的位移上限不變，但每秒步數變多** ——
5 Hz 配 5 mm 是 25 mm/s，30 Hz 配 5 mm 就是 150 mm/s。兩個參數要一起看。

> **用 `run_inference.sh`，不要直接 `docker compose up`。** monitor 是掛在
> `monitor` profile 下的獨立服務（`inference-monitor`），只有腳本會注入
> `--profile monitor`。`MONITOR_ENABLE=true` 這個環境變數只是傳給 launch 的
> 旗標，單獨設它推論會跑但**沒有任何東西寫 CSV**。腳本另外會以你的身分預建
> 輸出目錄；少了這步，容器會在 `monitor_output/` 留下 root 擁有的空檔，之後
> 連刪都要 sudo。

## 在兩種模式之間切換

只有**兩個變數**不同，其餘（DDS、HF 快取、extras、映像）完全共用。docker
compose 的 shell 環境變數優先於 `.env`，而 `run_inference.sh` 本來就是設計成
這樣用的（它還會從 `MODEL_PATH` 自動偵測 `ACTION_TYPE`），所以**不需要為了
換模式去改 `.env`**。

**關節空間：**

```bash
cd ~/Desktop/anvil/anvil-embodied-ai
MODEL_PATH=$PWD/model_zoo/smolvla_pack_pick_place_20260917/010000/pretrained_model \
CONFIG_FILE=./configs/lerobot_control/shapes/1arm_2cam.yaml \
CONTROL_FREQ=30.0 ./scripts/run_inference.sh --monitor-enable up
```

**末端空間：**

```bash
cd ~/Desktop/anvil/anvil-embodied-ai
MODEL_PATH=$PWD/model_zoo/smolvla_pack_pick_place_eef_5000 \
CONFIG_FILE=./configs/lerobot_control/shapes/1arm_2cam_ee.yaml \
CONTROL_FREQ=30.0 ./scripts/run_inference.sh --monitor-enable up
```

指令本身就寫明了跑的是哪一種，不必回頭去看 `.env` 現在是什麼狀態。

`IMAGE_TAG` 兩邊共用 `ee-space` 即可 —— 那個映像是 `latest` 加上
`anvil_msgs`，關節路徑完全不受影響，少一個要切的東西。

### loader 端不用跟著切

`commanded_ee: true` 是**增加**一條 EE 訂閱路徑，不是取代關節路徑。實測在
`openarm_v2_inference_commanded_ee.yaml` 之下：

```
/follower_r_forward_position_controller/commands   Subscription count: 2
/commanded_ee_right                                Subscription count: 2
```

兩條都在。所以 loader 可以一直留在 `openarm_v2_inference_commanded_ee.yaml`，
換模式時不必重啟 `ros2` 容器 —— 也就不必讓手臂再 homing 一次。

## 關機順序

```
1. 停推論
2. 從 Web UI 或 reset 服務下 dehome，等手臂放下來
3. 才 docker compose down
```

`docker compose down` 的 `pre_stop.sh` **只送一個分析事件到 Amplitude，不會放下
手臂**。關掉軟體不等於關掉馬達 —— 關節馬達會保持扭力鎖在最後的位置，這時候切
電源手臂會直接掉下來。
